# PDR-011: 서버 시작 알림은 즉시, 전수 후보 재계산은 안정화 뒤 수행한다

> 이 문서에서 PDR은 **Product Decision Record**를 뜻한다.

- 문서 상태: **DECISION**
- 상태: **Accepted / production**
- 결정일: **2026-08-17**
- 관련 ADR: [`ADR-014`](../server-spring/docs/ADR-014-stagger-provider-heavy-startup-work.md),
  [`ADR-015`](../server-spring/docs/ADR-015-reuse-current-company-notification-evidence.md)

## 사용자 문제와 목표

재배포 직후 startup 메시지는 빨리 받아야 하지만, 같은 순간 기업 277개의 분석·analyst·후보를 모두 다시
계산하면 화면 응답과 수집이 느려진다. 사용자는 즉시 기동 여부와 마지막 확정 후보를 확인하고, 최신 전수
재계산 결과는 시스템 안정화 뒤 받아야 한다.

## 제품 결정

1. 서버 시작 메시지는 기존처럼 영속된 latest snapshot과 후보 목록으로 즉시 발송한다.
2. 메시지의 후보는 새 계산인 것처럼 timestamp를 갱신하지 않는다.
3. 최신 기업 전수 후보 판정은 기동 20분 뒤 첫 시도한다. 기업 요약/analyst 작업이 아직 실행 중이면
   5분 간격으로 최대 6회 재시도하며, 신규 편입 조건을 충족하면 기존 편입 메시지 계약으로 알린다.
   2시간 이내의 완전한 기업 요약은 재사용하고, stale·부분 근거인 종목만 직접 재검증한다.
4. 정규 매시간 후보 스캔과 매수 조건은 변경하지 않는다.
5. 전수 재계산 지연은 `데이터 없음`, `후보 없음`, `매도`를 뜻하지 않는다.

## 채택하지 않은 안

- startup 메시지를 전수 계산 완료까지 지연: 기동 확인이 늦고 공급자 장애 시 메시지가 사라져 기각.
- 마지막 후보를 현재 재계산 결과로 표시: stale evidence를 현재값으로 오해시켜 기각.
- startup 전수 계산 자체를 삭제: 재배포 후 정규 cron 전까지 신규 후보 확인이 늦어져 기각.

## 성공 기준과 재검토

- startup 메시지는 기존 속도로 도착하고 서버 API가 provider 전수 작업과 즉시 경쟁하지 않는다.
- 20분 뒤 재계산과 bounded retry, 정규 스캔은 동일 후보 필터·outbox 중복 방지 계약을 사용한다.
- 중첩 감사 0건, API 5xx 0건, startup 구간 최대 지연을 후속 운영 감사에서 확인한다.
- 영속 snapshot이 신선도 상한을 넘으면 즉시 후보를 현재값처럼 보내지 않고 unavailable 계약을 우선한다.
